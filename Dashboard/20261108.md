# AIoT-Assisted Contactless Vital Sign Monitoring and Evaluation System

## Dashboard and Backend Software Requirements Specification

**Version:** 1.0  
**Date:** 8 November 2026  
**Project Type:** Final Year Project (FYP)

\---

## 1\. Project Background

The project aims to develop an AIoT-assisted contactless monitoring system for healthy ageing. The system integrates millimetre-wave radar sensing, environmental monitoring, edge artificial intelligence and a web-based dashboard.

The hardware platform is expected to use an R60ABD1 millimetre-wave radar module to acquire heart rate, respiratory rate and supported human-presence information. An ESP32-S3 development board will act as the main embedded controller, while an SHT31 sensor will measure ambient temperature and relative humidity.

An infrared thermal sensor array, such as the MLX90640, may be considered as an additional sensing component for non-contact surface-temperature monitoring. Its inclusion will depend on hardware approval and experimental feasibility.

The dashboard will provide a central interface for displaying real-time measurements, historical trends, AI-generated monitoring results and system status.

The software architecture should be modular and extensible, allowing additional sensors, machine learning models and data-analysis functions to be integrated without redesigning the entire system.

## 2\. Project Objectives

The software system shall:

1. Receive physiological and environmental measurements transmitted by the ESP32-S3.
2. Store sensor measurements in a structured cloud database.
3. Display real-time measurements and historical trends through a web dashboard.
4. Display AI model predictions and statistical anomaly information.
5. Support the evaluation of multiple machine learning models.
6. Provide an interface for natural-language queries through an external LLM API.
7. Support future integration of additional sensors and edge AI models.
8. Provide reliable data transmission, timestamp management and basic device-status monitoring.

## 3\. System Architecture

The proposed system consists of five main layers.

### 3.1 Sensing Layer

The sensing layer is responsible for collecting measurements from the physical environment and the monitored person.

Proposed sensors:

* R60ABD1 millimetre-wave radar: heart rate, respiratory rate and human-presence information.
* SHT31: ambient temperature and relative humidity.
* MLX90640 (optional): thermal image data and potential body-surface-temperature features.

Sensor measurements will be transmitted to the ESP32-S3 through the appropriate communication interfaces, including UART and I²C.

### 3.2 Edge Computing Layer

The ESP32-S3 will perform the following functions:

* Acquire data from connected sensors.
* Parse and validate sensor outputs.
* Attach timestamps and device identifiers.
* Perform basic data preprocessing.
* Execute a selected lightweight AI model locally, where feasible.
* Buffer data temporarily when Wi-Fi connectivity is unavailable.
* Transmit structured measurements to the cloud through HTTPS.

The ESP32-S3 should remain capable of collecting and processing sensor data independently of the dashboard.

### 3.3 Backend and Database Layer

Supabase will provide the cloud backend infrastructure.

The main services include:

* PostgreSQL: persistent sensor-data storage.
* Edge Functions: secure data ingestion and application API endpoints.
* Supabase Realtime: notification of new measurements to connected dashboard clients.
* Supabase Auth: optional user authentication and access management.

The ESP32-S3 will transmit JSON payloads to a dedicated HTTPS ingestion endpoint. The backend will validate incoming data before inserting it into the database.

Database credentials and privileged API keys must not be embedded in frontend code or exposed in public repositories.

### 3.4 Frontend Layer

The frontend will be developed using React, TypeScript and Vite.

Cloudflare Pages will host the built frontend application.

The dashboard shall be accessible through a standard web browser on desktop and mobile devices.

The frontend will communicate with Supabase using the appropriate public client configuration and access policies.

### 3.5 AI Query Layer

An API-based Large Language Model (LLM) function will be investigated as an additional dashboard feature.

Users may submit natural-language questions about recorded measurements and historical trends.

The backend will retrieve relevant sensor data and provide the necessary context to the LLM API. The LLM will generate explanations based on the retrieved information.

The LLM will not replace the embedded machine learning model or independently diagnose medical conditions.

## 4\. Functional Requirements

### 4.1 Dashboard Overview

The main dashboard shall display:

* Current heart rate (bpm).
* Current respiratory rate (breaths/min).
* Ambient temperature (°C).
* Relative humidity (%RH).
* Human-presence status, if supported by the radar output.
* Latest measurement timestamp.
* Device connectivity status.
* AI monitoring status.

Each measurement should include an appropriate unit and a timestamp.

If a sensor measurement is unavailable or invalid, the dashboard shall display an appropriate unavailable or invalid status instead of treating the value as zero.

### 4.2 Historical Data Visualisation

The dashboard shall provide time-series visualisation for:

* Heart rate.
* Respiratory rate.
* Ambient temperature.
* Relative humidity.
* Optional body-surface-temperature measurements.

Users should be able to select predefined time ranges, such as:

* Last 15 minutes.
* Last hour.
* Last 24 hours.
* Custom date range, where practical.

The dashboard should display measurement trends using line charts and provide basic summary statistics, such as minimum, maximum and average values.

### 4.3 AI Monitoring Results

The dashboard shall display outputs from the selected machine learning model.

Possible outputs include:

* Normal statistical pattern.
* Unusual statistical pattern.
* Model unavailable or insufficient data.
* Model confidence or anomaly score, where supported.

The system shall distinguish statistical anomalies from medical abnormalities.

The interface must not present model predictions as clinical diagnoses.

### 4.4 Model Comparison

The project will investigate approximately four to six candidate machine learning models.

Candidate models may include:

* Logistic Regression.
* Decision Tree.
* Random Forest.
* Extra Trees.
* Gradient Boosting.
* Isolation Forest.

The final model selection will depend on the availability of reliable labels and the defined prediction task.

Model comparison results will be generated during offline experiments using Python. The dashboard may include a model-comparison page displaying:

* Model name.
* Accuracy, where applicable.
* Precision.
* Recall.
* F1-score.
* Inference latency.
* Model size.
* Selected deployment model.

Supervised classification and unsupervised anomaly-detection results shall be evaluated separately where their tasks and labels differ.

### 4.5 AI Natural-Language Query

The dashboard shall provide a query interface allowing users to ask questions about recorded sensor data.

Example queries:

* "Show me the heart rate trend over the last hour."
* "Were there any unusual readings today?"
* "What was the average respiratory rate this morning?"
* "Show the relationship between ambient temperature and heart rate during the selected period."

The backend shall retrieve relevant database records and provide a limited, structured data context to the LLM API.

The LLM shall explain the available measurements and model outputs without inventing missing values or making unsupported clinical claims.

API credentials must be stored on the backend and must never be exposed in the frontend.

### 4.6 Device Status

The dashboard shall provide basic device-status information:

* Last successful data transmission.
* Device online or offline indication.
* Latest sensor update.
* Data transmission errors, where available.

A device shall be considered potentially offline if no valid data has been received within a configurable timeout period.

## 5\. Data Structure and Database Requirements

The initial database design shall include the following tables.

### 5.1 sensor\_readings

|Field|Type|Description|
|-|-|-|
|id|UUID|Unique record identifier|
|device\_id|TEXT|Device identifier|
|recorded\_at|TIMESTAMPTZ|Sensor measurement timestamp|
|heart\_rate|REAL|Heart rate in bpm|
|respiratory\_rate|REAL|Respiratory rate in breaths/min|
|ambient\_temperature|REAL|Ambient temperature in °C|
|humidity|REAL|Relative humidity in %RH|
|body\_surface\_temperature|REAL, nullable|Optional infrared surface-temperature measurement|
|presence|BOOLEAN, nullable|Human-presence information|
|temperature\_valid|BOOLEAN, nullable|Validity of optional surface-temperature data|
|created\_at|TIMESTAMPTZ|Database insertion timestamp|

The database should allow optional sensor fields to remain NULL when a measurement is unavailable.

### 5.2 ai\_predictions

|Field|Type|Description|
|-|-|-|
|id|UUID|Unique prediction identifier|
|device\_id|TEXT|Source device|
|recorded\_at|TIMESTAMPTZ|Prediction timestamp|
|model\_name|TEXT|Model identifier|
|model\_version|TEXT|Model version|
|prediction|TEXT|Model output|
|anomaly\_score|REAL, nullable|Optional model score|
|inference\_location|TEXT|Edge or backend|

### 5.3 model\_evaluations

This table or equivalent stored evaluation records may contain:

* Model name and version.
* Dataset identifier.
* Evaluation date.
* Accuracy.
* Precision.
* Recall.
* F1-score.
* Inference latency.
* Memory consumption.
* Model size.

The evaluation dataset and experiment configuration should be documented separately to ensure reproducibility.

## 6\. Data Transmission Requirements

The ESP32-S3 shall communicate with the Supabase backend through HTTPS.

The proposed transmission workflow is:

1. Read radar and environmental sensor outputs.
2. Validate and preprocess the measurements.
3. Generate a JSON payload containing the sensor values, device ID and timestamp.
4. Send an HTTPS POST request to the backend ingestion endpoint.
5. Validate the incoming payload on the backend.
6. Insert valid measurements into PostgreSQL.
7. Notify connected dashboard clients through Supabase Realtime, where enabled.

An illustrative JSON payload is:

```json
{
  "device\_id": "aiot\_device\_001",
  "recorded\_at": "2026-11-08T10:00:00Z",
  "heart\_rate": 76.0,
  "respiratory\_rate": 16.0,
  "ambient\_temperature": 24.5,
  "humidity": 55.0,
  "body\_surface\_temperature": null,
  "presence": true,
  "temperature\_valid": false
}
```

The values above are examples only.

The initial transmission interval should be configurable. A practical prototype may initially send measurements every few seconds or transmit small batches, depending on the radar output rate and network stability.

The ESP32-S3 should use a secure device-specific authentication mechanism. A privileged Supabase service-role key must never be stored in the firmware.

The firmware should implement basic retry and temporary buffering mechanisms to reduce data loss during network interruptions.

## 8\. Security and Reliability Requirements

The system shall follow these requirements:

1. All communication between the ESP32-S3 and cloud backend shall use HTTPS.
2. Privileged database credentials shall not be exposed in frontend code or firmware.
3. Database Row Level Security (RLS) shall be configured for appropriate access control.
4. Device authentication shall be separated from ordinary frontend user authentication.
5. Invalid or incomplete sensor measurements shall be handled explicitly.
6. Sensor timestamps and database insertion timestamps shall be stored separately.
7. The ESP32-S3 shall implement basic handling of temporary network failures.
8. API keys for external LLM services shall be stored securely on the backend.
9. Only the minimum data required for a query shall be sent to the external LLM service.
10. The system shall not claim medical diagnostic capability.

## 11\. Scope and Limitations

The initial implementation will focus on heart rate, respiratory rate, ambient temperature and relative humidity.

Additional infrared surface-temperature sensing may be included if hardware availability, cost and measurement reliability permit.

The system will focus on statistical monitoring and the identification of unusual measurement patterns. It will not claim to diagnose diseases, determine clinical risk or replace professional medical assessment.

Public datasets will support preliminary model development. However, final system evaluation will also require measurements collected using the actual hardware prototype.

Synthetic data may be used for controlled experimentation or data augmentation, but it shall not replace independent real-world validation.

The dashboard and backend will be designed to support future extensions without requiring major changes to the core architecture.
